# Протокол валидации и приёмочного тестирования FanPay Team Dashboard v2.4

Данный документ регламентирует порядок всесторонней проверки развёрнутой схемы базы данных FanPay Team Dashboard v2.4, целостности ограничений, политик безопасности RLS, сигнатур RPC-функций и методику 5-уровневой сверки при миграции данных из локального кеша расширения Chrome.

---

## 1. Автоматизированная валидация: скрипт `009_validation.sql`

Скрипт [`009_validation.sql`](./009_validation.sql) выполняется в **Supabase SQL Editor** после применения миграций `001`–`008`.

Скрипт разделён на две фундаментально изолированные части:
1. **Часть 1 (Статический аудит каталогов, Read-Only):** проверяет схему, RLS-политики, права, триггеры, индексы и сигнатуры функций без изменения данных.
2. **Часть 2 (Динамические интеграционные тесты, Unconditional ROLLBACK):** проверяет поведение транзакционной логики, ограничений и триггеров на реальных вызовах с моком JWT claims, завершаясь безусловным `ROLLBACK`, гарантирующим нулевой след в базе.

## 2. Детальная структура проверок `009_validation.sql`

### 2.1. Часть 1: Статический аудит (Read-Only)

Статический блок опрашивает системные таблицы `information_schema` и `pg_catalog`:

1. **Наличие всех 8 таблиц схемы v2.4:**
   - `profiles`, `team_seller_accounts`, `shifts`, `operator_status`, `orders`, `order_audit_logs`, `order_financial_discrepancies`, `shared_templates`.
2. **Активация Row Level Security (RLS):**
   - Проверяется флаг `c.relrowsecurity = true` в `pg_class` для каждой таблицы.
3. **Проверка существования 14 критических RLS-политик:**
   - Включая `profiles_select_policy`, `team_seller_accounts_select`, `shifts_select_team`, `orders_select_policy`, `order_discrepancies_select_owner` и др.
4. **Наличие уникальных индексов и бизнес-ограничений:**
   - Частичный уникальный индекс `idx_shifts_one_active_per_user` на `shifts (user_id) WHERE status = 'active'`.
   - Ограничение уникальности горячих клавиш `uq_shared_templates_shortcut` на `shared_templates`.
   - Ограничение дедупликации инцидентов `uq_order_discrepancy` на `order_financial_discrepancies`.
5. **Сигнатуры ключевых функций и RPC:**
   - `is_active_team_member()` — без параметров (исключает side-channel зондирования).
   - `is_team_owner()` — без параметров.
   - `bootstrap_initial_owner(uuid)`.
   - `sync_orders_batch(text, jsonb)`.
   - `reassign_order_operator(text, text, uuid, text)`.
   - `recalculate_shift_attributions(uuid, timestamp with time zone, timestamp with time zone)`.
6. **Изоляция безопасности функций (SECURITY DEFINER & search_path):**
   - Все привилегированные функции имеют флаг `prosecdef = true` и `search_path=public, pg_temp` для защиты от подмены объектов.
7. **Отзыв прямых прав на изменение заказов и аудита:**
   - Для ролей `authenticated`, `anon` и `PUBLIC` полностью отсутствуют прямые права `INSERT`, `UPDATE`, `DELETE` на `orders`, `order_audit_logs`, `order_financial_discrepancies`.
8. **Регистрация защитных триггеров:**
   - `trg_protect_profile_fields`, `trg_protect_shift_fields`, `trg_validate_operator_status`, `trg_protect_order_fields`, `trg_shared_templates_audit`.
9. **Начальное наполнение общих шаблонов (F1–F8):**
   - Проверка наличия ровно 8 записей.

---

### 2.2. Часть 2: Интеграционные динамические тесты (ROLLBACK)

Динамический блок выполняется внутри транзакции `BEGIN ... ROLLBACK`:

#### Автоматическая инициализация Mock JWT Claims
При запуске скрипта из Supabase SQL Editor сессия по умолчанию не имеет пользовательского JWT токена (`auth.uid()` равен NULL).
Скрипт автоматически настраивает тестовый контекст вызовом:
```sql
PERFORM set_config('request.jwt.claims', json_build_object(
    'sub', v_test_user_id::text,
    'role', 'authenticated'
)::text, true);
```
Это позволяет протестировать реальные RPC-функции в контексте аутентифицированного оператора без предварительной ручной авторизации в веб-интерфейсе.

#### Выполняемые тесты:
1. **Тест лимита пакета заказов (`sync_orders_batch` > 50):**
   - Генерируется JSON-пакет из 51 заказа; ожидается перехват исключения о превышении лимита в 50 заказов.
2. **Тест строгой валидации формата суммы:**
   - Передаётся заказ с суммой `100.555` (3 знака после запятой); проверяется отклонение до приведения типа.
3. **Тест запрета параллельных активных смен:**
   - Попытка открыть вторую смену одному пользователю; проверяется перехват `unique_violation` частичным индексом.
4. **Тест запрета открытия смены на неактивном магазине:**
   - Попытка открыть смену на магазине с `is_active = false`; проверяется отклонение триггером.
5. **Тест триггера иммутабельности полей заказа:**
   - Попытка прямого обновления суммы заказа через `UPDATE public.orders SET amount = 999`; проверяется блокировка триггером `trg_protect_order_fields`.

#### Завершение транзакции:
- Завершается безусловным оператором `ROLLBACK;`. База данных остаётся абсолютно чистой.

## 4. Протокол 5-уровневой контрольной сверки миграции данных

При переносе данных из локального хранилища Chrome Extension (`fphk_cache.orders`) в Supabase выполняется сверка:

### Уровень 1: Сверка множеств идентификаторов (Set Equality)
Каждый номер заказа из локального хранилища должен существовать в таблице `orders` в рамках магазина:
$$\{ \text{ID}_{\text{local}} \} \setminus \{ \text{ID}_{\text{cloud}} \} = \emptyset$$

```sql
SELECT seller_account_id, order_id, COUNT(*) 
FROM public.orders 
WHERE seller_account_id = :seller_id 
GROUP BY seller_account_id, order_id 
HAVING COUNT(*) > 1;
-- Ожидается: 0 строк (строгий составной PK)
```

### Уровень 2: Контрольная сумма оборота по валютам (Financial Checksum)
Сумма `amount` по каждой валюте для подтверждённых заказов (`status = 'closed'`) должна точно совпадать:
```sql
SELECT 
    currency, 
    COUNT(*) AS total_orders,
    SUM(amount) FILTER (WHERE status = 'closed') AS closed_turnover,
    SUM(amount) FILTER (WHERE status = 'paid') AS active_escrow,
    SUM(amount) FILTER (WHERE status = 'refunded') AS refunded_sum
FROM public.orders
WHERE seller_account_id = :seller_id
GROUP BY currency
ORDER BY currency;
```
> [!IMPORTANT]
> **Исключение двойного вычета:**
> Подтверждённый оборот формируют только заказы со статусом `closed`. Возвраты (`refunded`) исключены естественным образом. Дополнительно вычитать сумму возвратов из `closed_turnover` запрещено.

### Уровень 3: Сверка распределения статусов (Status Distribution)
Количество заказов по статусам (`paid`, `closed`, `refunded`) должно совпадать:
```sql
SELECT status, COUNT(*) AS count
FROM public.orders
WHERE seller_account_id = :seller_id
GROUP BY status
ORDER BY status;
```

### Уровень 4: Хеш-верификация ключевых полей (Sampling SHA-256)
Для выборки из 50 заказов вычисляется хеш неизменяемых данных:
$$\text{SHA256}(\text{order\_id} \mathbin{\Vert} \text{amount} \mathbin{\Vert} \text{currency} \mathbin{\Vert} \text{funpay\_created\_at} \mathbin{\Vert} \text{COALESCE(buyer\_id, '')})$$

### Уровень 5: Аудит журнала финансовых расхождений
```sql
SELECT * FROM public.order_financial_discrepancies WHERE seller_account_id = :seller_id;
-- Ожидается 0 записей при чистом импорте
```

## 5. Таблица диагностики и устранения типовых сбоев

| Ошибка валидации | Причина | Способ устранения |
| :--- | :--- | :--- |
| `ОШИБКА: Отсутствуют таблицы...` | Не применён один из файлов `001`–`007` | Выполнить пропущенный SQL-файл миграции по порядку номеров. |
| `ОШИБКА: RLS отключён на...` | Пропущена директива `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` | Применить соответствующий файл миграции повторно. |
| `ОШИБКА: Не найдены функции с ожидаемыми сигнатурами...` | Устаревшая сигнатура (например, наличие параметров в `is_active_team_member`) | Пересоздать функции через `001_profiles_and_auth.sql` и `008_rpc_functions.sql`. |
| `ОШИБКА: Обнаружены небезопасные прямые права INSERT/UPDATE...` | Не выполнен отзыв привилегий (`REVOKE`) | Выполнить секции `REVOKE` из `004_orders.sql`, `005_order_audit_logs.sql`, `006_financial_discrepancies.sql`. |
| `Не удалось инициализировать mock JWT claims` | Специфическая конфигурация прав на `set_config` | Убедиться, что сессия в SQL Editor имеет доступ к настройке GUC-переменных запроса. |
